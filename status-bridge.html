D7 MeLi OAuth & API — 7 hallazgos (1 Alto, 3 Medios, 3 Bajos)
D7.1 Worker sin refresh inline de token: ml_get() en inbound_worker.py lanza RuntimeError("token_expired") en HTTP 401 pero NUNCA intenta refrescar el token. Depende 100% del cron cada 6h. Si el cron falla (como pasó el 8/may 01:07 UTC por permisos en /tmp), todas las órdenes MeLi fallan durante horas hasta intervención manual. El refresh exitoso fue a las 07:15 UTC, pero para entonces ya había 36 dead orders. Mitigación inmediata: agregar inline refresh en ml_get() cuando recibe 401, usando /oauth/refresh o llamando al refresh script. ✅ Corregido Alta
D7.2 "Circuit breaker" es solo un comentario: El header en inbound_worker.py dice "Con retry y circuit breaker pattern" pero no existe ninguna implementación de circuit breaker. Si MeLi API está caída o el token es inválido, el worker sigue golpeando la API indefinidamente con cada job de la cola, sin backoff global ni ventana de apertura. Esto agrava rate limiting y genera carga innecesaria. 🔴 Pendiente Media
D7.3 No hay detección de refresh token expirado / revocado: Si el usuario revoca la aplicación en MeLi o el refresh token expira, meli_refresh_tokens.sh falla con invalid_grant y el worker sigue reportando token_expired indefinidamente. No hay mecanismo para detectar este caso especial ni forzar re-autenticación OAuth (redirigir a /oauth/start). El script de refresh tampoco notifica vía webhook/email/alerta. 🔴 Pendiente Media
D7.4 Rate limit 429 sin tracking de headers: MeLi API devuelve X-Rate-Limit-Limit, X-Rate-Limit-Remaining y X-Rate-Limit-Reset. El worker solo hace retry ciego exponencial (base 2s) sin leer estos headers. El 8/may 01:02 UTC MeLi respondió 429 local_rate_limited; el retry ciego puede empeorar la situación. Se debería leer Retry-After o X-Rate-Limit-Reset para backoff adaptativo. ✅ Corregido Media
D7.5 OAuth Authorization Code flow sin PKCE: Aunque es server-side, OAuth 2.0 BCP (RFC 7636) recomienda PKCE para todos los clients. El endpoint /oauth/start no genera ni envía code_challenge/code_verifier. Mitigación parcial: el state CSRF está bien implementado con Redis GETDEL. 🔴 Pendiente Baja
D7.6 Callback no requiere refresh_token obligatoriamente: Si MeLi no devuelve refresh_token (ej. usuario ya autorizó antes y MeLi no lo reemite), /oauth/callback guarda igual el access_token y solo emite un warning. Esto resulta en un token que expira en 6h y nunca se puede refrescar. Debería requerir refresh_token para considerar el callback exitoso, o al menos enviar alerta. 🔴 Pendiente Baja
D7.7 Lectura de token file sin manejo de corrupto: ml_token() lee /data/.meli_tokens.json directamente con json.load(). Si el archivo está medio escrito (crash durante cp en el refresh script) o corrupto, el worker crashea con json.JSONDecodeError en vez de manejar el error gracefulmente (ej. loggear y tratar como token_expired). ✅ Corregido Baja
